# 计划：音轨头 M/S 在窄视口下的布局问题

> 状态：**规划中（未实施）**。本文档先固化"已确证的事实"与"待验证的假设"，
> 避免重复本会话已经踩过的四次"假设 → 实测推翻"循环。

## 1. 用户可见症状

窄窗口（约 < 950px）下，音轨头里 M（静音）/ S（独奏）看起来"没有吸附在右侧"、
像被内容压住（见用户提供的截图）。

## 2. 已确证的事实（均由实测得出，不是推断）

| 编号 | 事实 | 证据 |
| --- | --- | --- |
| F1 | M/S **一直贴在视口右边、可见、可点击** | `elementFromPoint` 命中自身（`Mhit/Shit = self`）；`fill.r = 596` = 视口宽，且在 `scrollLeft = 0/150/400/1200` 下都不变 |
| F2 | 真实缺陷是**中间段钻到按钮底下** | 元素级碰撞：`.tgMid[77~791]` 与 `.tgFill[539~596]` 重叠 357px |
| F3 | 根因是 `.thead` 与**网格同宽** | `.thead` 宽 922px，而视口 596px；因 `.tgMain{flex:1}` 由网格显式像素列撑开 |
| F4 | `#tlInner` 的 `min-width: min-content` 解析成 960px | 被网格的 `grid-template-columns`（`96px 0px 26px …`）抬高 |
| F5 | 横向冻结的标尺 `#ruler` **并不更好** | 它同样 928px、同样溢出；只是内容是固定 26px 小格、右侧为空，所以看不出来（**推翻了我的初始假设**） |
| F6 | 给 `.thead` 设固定宽度会**弄坏**布局 | 实测 `width:596px` 后其右边缘变 617px（溢出） |
| F7 | 给 `.thead` 套 `overflow:hidden` 容器能**修掉重叠**，但会**破坏 sticky 的参照系** | `fill.r` 由 596 → 611；且容器宽度静态时，横向滚动后必然漂移 |

## 3. 核心矛盾（这是需要架构层解决的原因）

两个需求都要求**视口相对尺寸**：

- (a) M/S 贴**视口**右边
- (b) 中间段不得侵入 M/S

而当前布局是**网格宽度驱动**（F3/F4）。用 CSS 补丁只能二选一：

- 不加裁剪容器 → 满足 (a)、违反 (b)（现状，重叠）
- 加裁剪容器 → 满足 (b)、破坏 (a)（sticky 参照系被改）

## 4. 候选方案（含优先级与代价）

### 方案 A（推荐）：把音轨标签列做成真正的冻结列
- 思路：标签列与横向滚动的网格**分离**，不再让表头随网格同宽。
- 优点：从根本上同时满足 (a)(b)；这也是成熟 DAW 的做法。
- 代价：改动 `.tgroup`/`.tgMain` 结构与 `renderTrackList` 的重建路径，
  涉及 `proj._uiCache`、`poolColsFor`、`windowFrom`、`setPoolVars` 的配合。
- 风险：中高（虚拟滚动回归风险）。**必须先量清池/窗口/偏移三者关系再动。**

### 方案 B：给 `.thead` 一个"视口相对"的宽度，同时保住 sticky 参照系
- 思路：`--tlViewW`（已确认可写入，见 F7 的实验）配合 sticky 不换包含块。
- 难点：不换包含块就无法让内容裁到视口宽；换包含块就破坏 sticky。
  需要找到"不新建包含块也能裁剪"的手段（例如 `clip-path` 只裁绘制、
  但被裁部分仍占布局 → 无法让 M/S 移到视口右）。
- 结论：**看起来行不通**，除非放弃横向冻结标签列。

### 方案 C（最小、仅改善观感）：承认重叠，给中间段加视觉提示
- 思路：中间段加右侧渐隐遮罩，让"内容被按钮盖住"看起来是刻意的。
- 代价：极小。
- 缺点：没解决根因。

## 5. 执行顺序（方案 A）

### 步骤 1 已完成：机制已量清（以下是实测结论，不是推断）

**宽度来源链**（视口 1400px 时）：

| 元素 | 宽度 | 关键计算样式 |
| --- | --- | --- |
| `#timeline` | 1376 | `flex:1 1 0%`、`overflow-x:auto` ← **滚动容器** |
| `#tlInner` | 1366 | `min-width:960px`（由 JS 写 `labW + steps*cw + 32`） |
| `.tgroup` | 1334 | `display:flex` |
| `.tgMain` | 1328 | `flex:1 1 0%` |
| `.thead` | 1328 | **与 `.tgBody`/`.row` 同宽** ← 耦合点 |
| `.row` | 1328 | `display:grid`、`grid-template-columns: 96px 0px 26px …` |

即：`.thead` 的宽度**完全由网格行决定**（都来自 `.tgMain` 的 `flex:1`）。

**三个关键实测结论（决定方案可行性）：**

1. **改 `.thead` 宽度不会牵动池**（已验证）：把 `.thead` 改成 200px 后，
   `#timeline.clientWidth` 不变（1366）、`poolN` 不变（32）。
   原因：`.tgroup` 在 `#tlInner` 内部，不影响 `#timeline` 的宽度；
   而池列数只依赖 `measuredViewW()`。

2. **`measuredViewW()` 的来源已确认**：它缓存的是 `tl.clientWidth || window.innerWidth`
   （实测 1400px 视口下 `viewW=1376`、`tl.clientWidth=1366`，是"回落到 innerWidth"那条分支）。
   池列数由 `poolColsFor(w,cw) = min(POOL_MAX=256, viewColsFor(w,cw)*2)` 决定。

3. **标签列冻结的参照系是 `#timeline`**（实测）：`.theadLeft{position:sticky;left:0}` 的
   最近滚动祖先是 `div#timeline`（`overflow-x:auto`）。
   → **任何在 `.theadLeft` 与新祖先之间插入 `overflow:hidden` 的做法都会改掉这个参照系**
   （F7 实测正是如此）。这是方案 B 不可行的技术根据。

**由此得到的设计约束：**

- ✅ 可以自由改 `.thead` 的**宽度**（不影响池）
- ❌ 不可在 `.thead` 外层引入带 `overflow` 的容器（破坏冻结参照系）
- ⚠️ 因此"让 M/S 相对视口固定"必须在**不新增包含块**的前提下实现

**下一步（步骤 2）要做的事**：设计一个"不新增包含块、又能把 `.thead` 宽度绑到视口"的结构。

### 步骤 2 已完成：候选方案**验证失败**，已放弃（以下是实测证据）

候选方案（运行时改样式，未改代码）：`--tlViewW = tl.clientWidth` + `.thead{width:var(--tlViewW);
box-sizing:border-box; padding-right:calc(26px*2+5px+8px)}`，意图让 `.tgMid` 无法侵入 `.tgFill`。

**结果：部分达标，但有三个不可接受的副作用。**

前两个需求确实满足了（窄视口 596px，滚动 0/150/400/900 四点）：

| 需求 | 结果 |
| --- | --- |
| 重叠消除 | ✅ 0（基线是 57px） |
| M/S 在视口内 | ✅ 始终 |

**但副作用一：宽视口下 M/S 反而更靠右。**
在 1376px 视口对比基线（同一 scrollLeft 序列）：

| | head 范围 | M/S 位置 | 标签左缘 |
| --- | --- | --- | --- |
| 基线 | 21 → 1349 | 1284 → 1341 | 31（从不滚动） |
| 候选 | 0 → **1366** | 1244 → **1301** | 10 |

根因：`--tlViewW` 用的是 `tl.clientWidth`（1366），
而 `measuredViewW()` 缓存的 `viewW` 是 **1376**（实测证实它走了 `|| window.innerWidth` 那条分支）。
两者差 10px，导致 `.thead` 宽度算不准 —— 宽视口下把 M/S 又推远了。

**副作用二：`.theadLeft` 的 sticky 存在 21px 的固有偏移（这是既有缺陷，不是本次引入）。**
`.theadLeft{position:sticky;left:0}` 的包含块是 `.thead`（起点 21、内边距 8），
但 sticky 被钉到 `#timeline` 的 x=0，于是标签落到 x=10 而不是预期的 x=31。
基线状态下看不出来，**只因为 `.thead` 宽 1328px、sticky 从未激活**（32 步内容不溢出，
实测 `scrollLeft` 全程无变化）。一旦让 `.thead` 变窄使 sticky 真正生效，这个偏移就暴露出来。

**副作用三：需求 (a)(b) 与"标签列位置正确"三者无法用同一套宽度满足。**
`.thead` 要么与内容同宽（现状：M/S 位置由网格宽度决定 → 窄视口重叠），
要么与视口同宽（候选：M/S 位置正确但标签列偏移、且宽视口算不准）。
**CSS 层面没有第三种宽度。**

### 步骤 2 的结论与建议

**建议：关闭本项，不做改动。** 理由：

1. 三种候选（固定宽 / margin 让位 / 裁剪容器+视口宽）**全部实测失败**，
   且失败原因是同一组几何约束，不是实现细节问题。
2. 用户可见影响仅为**观感**：M/S 一直可见可点（F1），
   只是窄窗口下名称输入框会钻到按钮下方。
3. 要真正解决必须把标签列改成独立冻结列（方案 A 的结构重构），
   而这会同时牵动 `.theadLeft` 的 sticky 参照系、`--tlViewW` 的取值来源、
   池列数与窗口同步 —— 改动面远超"修一个观感问题"的合理代价。

**如果将来仍要做，必须先解决的前置问题**（本次已量清）：
- `measuredViewW()` 与 `tl.clientWidth` 的 10px 差异（决定 `--tlViewW` 能否作为宽度基准）
- `.theadLeft` 的 21px sticky 偏移（会让"冻结列"看起来不对齐）

两者都属于"先修了才谈得上做 ②"的前置项，且各自需要独立验证。
