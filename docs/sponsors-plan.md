## 一、目标与不做什么

### 目标
1. 在应用内和 README 中展示感谢赞助者（自愿、可匿名）。
2. 名单可维护，不依赖手工改代码。

### 明确不做（第一版）
- **不做权限/权益解锁**：本项目是 MIT、无功能锁，赞助不应改变功能可用性。
  一旦名单与权限挂钩，就变成"付费功能"，与 README 的承诺冲突。
- **不做自动支付校验**：见下方"方案 B"的评估。
- **不做实时同步**：名单是低频数据，没必要引入定时拉取。

## 二、已确证的事实（实施时可直接依赖，不必重查）

### 2.1 爱发电侧
- 创作者主页形如 `https://afdian.com/a/<slug>`（本项目为 `yhl14122`）。
- **匿名访问时服务端不下发创作者昵称**：实测浏览器打开该页，页面文本里
  既没有「银狐林」也没有创作说明（但页面不是 404、有「为TA发电」按钮）。
  → **不能靠抓页面来校验"某人是这个创作者的赞助者"**。
- 爱发电有「开放 API」（`user_id` + `token`），但：
  - 需要后端保存密钥；本项目是纯前端 + 一个只做 KV 读写的分享后端，**不适合**放支付密钥；
  - 其用途是"校验订单/发放权益"，而本规划**不打算发权益**（见"不做"）。
  → 结论：**第一版不接 API，名单用人工维护的静态数据**。

### 2.2 本项目的可扩展点（都已存在，无需新造）
- **`hooks` 晚绑定注册表**：`js/core/util.js` 导出 `hooks`，各模块用 `hooks.xxx=` 直接赋值
  （`main.js` → inspector/ui/undo/afterLoad/save；`seek.js` → seek；`sidebar.js` → sidebar；
  `toolbar.js` → toolbar）。**新增 UI 区块不需要动这些既有模块**，可照 `ui/sponsor.js`
  做成自包含模块（自己在容器里插 DOM 并自绑事件）。
- **`ui/sponsor.js` 已建好配置模式**：读 `<meta name="afdian-url">`，
  未配置（含仍是占位符）时**不插入任何 DOM**。感谢名单应沿用同一模式：
  `<meta name="sponsors-url">` 之类的配置项，未配置则整块不出现。
- **`localStorage` 键名约定**：主存档 `musicProducerPro.v1`（`core/storage.js` 的 `LS_KEY`）、
  作品库 `LIB_KEY`、可视化移交 `vizProject`、短链后端 `mpApiBase`、主题 `mpTheme`、
  站点基址 `LS_SITE_KEY`。**新增名单缓存请另起独立键**（例如 `mpSponsors`），
  不要塞进主存档 —— 那会让每次自动保存都带上无关数据，并可能触发配额降级。
- **存储配额已被处理**：`io/project.js` 的 `autosaveNow()` 在
  `QuotaExceededError` 时会先 `archiveClear()` 再重试。名单缓存虽小，但仍应 `try/catch`
  （隐私模式下 localStorage 可能直接抛异常）。
- **安全写法已有先例**：`ui/sponsor.js` 里对 URL 做了白名单校验
  （只接受 https + `afdian.com` 域，拒绝子域名伪装与 `javascript:`）。
  **名单里的任何 URL（赞助者主页/头像）都必须走同样的校验**，否则等于给自己开了一个 XSS 入口。
  另：全仓 `innerHTML` 只接收静态文案/内部常量/数字，载荷字符串一律走
  `value`/`title`/`textContent` —— 名单里的**昵称是外部数据**，
  必须走 `textContent`（或 `el(...,{text})`），**绝不可拼进 innerHTML**。
- **`icon()` 可用图标**：项目用 CSS mask 线性图标，`icon(name)` 会做
  `replace(/[^a-zA-Z0-9-]/g,'')` 白名单。`--ic-coffee` 已存在（赞助入口在用）。

## 三、方案对比

### 方案 A：静态名单（推荐第一版）
名单写在 `docs/sponsors.md`（或 `js/data/sponsors.js`），应用内读取并渲染。

| | |
|---|---|
| 数据来源 | 人工维护的静态文件 |
| 后端 | 不需要 |
| 校验 | 不需要 |
| 优点 | 零成本、零风险、可控、随时可改 |
| 缺点 | 需手工更新；无法自动反映新赞助者 |
| 隐私 | 可只列昵称、可匿名、可要求下线 |

**适用判断**：赞助者数量在可预见的未来是"几个到几十个"量级，
人工维护完全够用。**不要为不存在的规模问题预先设计。**

### 方案 B：接爱发电开放 API 自动同步（不推荐）
需要一个持有 `user_id`/`token` 的后端定时拉取订单列表 → 构造名单。

不推荐的理由：
1. **密钥必须放服务端**，而现有后端（`server/handler.js`）是"匿名 KV 读写"的极简设计，
   引入支付密钥会显著扩大攻击面与责任范围；
2. 本规划**不发放权益**，所以"自动校验订单"没有实际用途
   —— 它解决的是"确认某笔付款"，而静态名单只需要"我确认过"；
3. 任何自动同步都需要一个"公开展示谁赞助了"的同意流程，而这在人工维护下
   天然成立（我会先问过对方）。

### 方案 C：让赞助者自己提交（不推荐第一版）
开源仓库的 PR/Issue 表单。问题：任何匿名人都能提交自己的名字/链接
（等于向所有用户展示未审核的外链）。**若要做，必须"仅接受我审核过的条目"**，
那就退化成方案 A 了。

## 六、风险与注意事项

- **不要把名单塞进主存档**：会污染自动保存、可能触发配额降级逻辑。
- **昵称是外部数据**：must 用 `textContent`。这是唯一有安全含义的点。
- **赞助者隐私**：只展示本人同意展示的信息；提供便捷的下线通道。
- **不要暗示"赞助=获得功能"**：README 已承诺"全部功能免费、无功能锁"，名单页面文案要一致。
- **爱发电页面无法被匿名抓取验证**（见 2.1），所以**不要**在实现里依赖
  "自动确认某人是赞助者"——人工确认是这一版的前提。
